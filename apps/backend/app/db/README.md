# PostgreSQL foundation

Install backend requirements and run `DATABASE_URL=... python -m app.db.migrate` from `apps/backend` with a dedicated migration owner. Migrations run atomically and are tracked in `schema_migrations`. Use a fresh, empty disposable database for the complete integration suite; the backfill test runs first and the suite is not parallel-safe:

```
TEST_DATABASE_ADMIN_URL=... TEST_DATABASE_RUNTIME_URL=... python -m pytest tests/db -q
```

The admin URL must be a superuser in the disposable test database; the runtime URL must be a separate non-superuser role without BYPASSRLS. In deployment, grant the application role only the table privileges it needs, never ownership, BYPASSRLS, superuser, or membership in a privileged role. Migrations and provisioning require a separate privileged path. The application and workers should use `tenant_session(url, authorized_tenant_id)` for every tenant transaction; the helper does not authenticate users or decide authorization. Context is transaction-local and absent context denies tenant rows.

Users are global identities and are not protected by tenant RLS. Future endpoints must limit user data and enforce membership, event and participant authorization; tenant RLS alone does not provide those guarantees. Tenant provisioning requires a separately controlled privileged access path. Existing endpoints and workers do not yet use this layer.

## Public hostname context rollout

Apply migration 002 with a dedicated migration role that has BYPASSRLS (or is a superuser): its backfill reads `tenant_domains`, which has FORCE RLS, and `row_security = off` deliberately fails rather than silently omit rows. The migration owner owns the private lookup table and SECURITY DEFINER functions. Do not grant runtime role membership in that owner, ownership of these objects, or BYPASSRLS. Existing domains are copied during migration; subsequent changes are synchronized transactionally by a trigger.

After migration, an administrator must provision each existing or new runtime role explicitly, including during rollout:

```
DATABASE_URL=<migration-owner-url> python -m app.db.provision_context <runtime-role>
```

This grants execute on the narrowly scoped lookup function, SELECT on RLS-protected tenants and branding, and schema usage; it revokes direct privileges on the private lookup table from that role. Ensure the role has no indirect grants via PUBLIC or role memberships and cannot create objects in trusted schemas. The command does not remove unrelated existing grants. The endpoint accepts only a validated Host header, ignoring X-Forwarded-Host; the ingress must preserve the validated external Host. Reserved first labels are admin, api, auth and www. Unknown or suspended tenants return 404. The endpoint is public identity/branding only and does not authorize any legacy route.

## Application session and event access

Apply migration 003 and rerun `python -m app.db.provision_context <runtime-role>` with the migration-owner URL. It grants the runtime role access to global users, tenant-scoped sessions and login challenges, and RLS-protected events, memberships and participations. The runtime role must remain non-owner, non-superuser and without BYPASSRLS or privileged inherited roles. Users are global: database access to that table is not tenant isolated; application authorization remains essential.

The new, separate API uses `POST /api/v1/session/challenge` to create a one-use five-minute nonce and host-only secure challenge cookie. The client must obtain a Google ID token with that exact nonce and the configured `GOOGLE_CLIENT_ID` as audience, then send it to `POST /api/v1/session/google` from the same HTTPS origin. The server verifies Google's signature, issuer, audience and expiration and identifies the user by subject, never by email. Both challenge and session records are bound to the canonical hostname, including when one tenant has multiple domains. The eight-hour host-only session is HttpOnly, Secure and SameSite=Strict; only its hash is stored. `GET /api/v1/session` identifies the session, and `DELETE /api/v1/session` requires the `X-CSRF-Token` header matching the `__Host-fm_csrf` cookie and the same HTTPS Origin. It revokes the session server-side. `GET /api/v1/events/{id}` returns a tenant's event to an owner/admin, or a published event to a linked participant; other event IDs return 404. Tenant comes only from Host, not the client body.

This is a backend primitive: there is no frontend login integration, central OAuth callback or cross-subdomain handoff. Google client configuration must permit the chosen login flow and HTTPS origin. Expired challenge/session cleanup, rate limits, session management UI, and policies for closed events remain to be implemented. Existing Drive OAuth, indexing, searches, admin routes and workers remain legacy and are not protected by these new sessions or event checks. Provisioning memberships and participations remains a privileged operation.

## Event gallery (separate from legacy index)

Apply migration 004, rerun `python -m app.db.provision_context <runtime-role>` and restart API and Celery workers. The worker must use a non-owner, non-BYPASSRLS runtime role. New endpoints: `POST /events/{event_id}/gallery/index` with JSON `{"folder":"<public Drive folder>"}`, `GET /events/{event_id}/gallery/jobs/{job_id}`, `POST /events/{event_id}/gallery/search` with multipart `selfie`, and `GET /events/{event_id}/gallery/searches/{search_id}/photos/{photo_id}`. Mutations require same HTTPS Origin and the session CSRF header. Indexing and job status require owner/admin; search requires event access; media requires both current event access and ownership of the search result. No legacy Drive index, Redis image cache, or Google file URL is used for delivery.

The worker receives explicit IDs, checks job state and organizer membership before processing and again before replacing the event's photos. It stores normalized JPEGs and face vectors in PostgreSQL under tenant RLS. A successful reindex replaces the event photos and invalidates old media results. Limits for this preliminary implementation are 30 photos, 8 MiB per image, 20 million pixels, one active index job per event, and 5 MiB per selfie. Comparison scans vectors in Python; no scaling, versioned model or deletion/retention is implemented. Selfies are not persisted; image bytes, embeddings and search metadata are persisted and need a retention policy. A public Drive folder remains publicly accessible at its original source; application access control does not make that source private. Existing legacy routes remain separate and public as before.

Gallery recovery requires a separate database role without BYPASSRLS: provision it with `DATABASE_URL=<migration-owner-url> python -m app.db.provision_gallery_dispatcher <dispatcher-role>`, configure `GALLERY_DISPATCHER_DATABASE_URL` for Celery workers and run one Celery beat scheduler. The dispatcher can enumerate pending job/tenant/event IDs across tenants, but receives no photo data. Protect its credentials and do not grant membership in privileged roles. Every minute beat republishes queued jobs older than 30 seconds and jobs with expired ten-minute leases. A lease token prevents a stale worker from replacing photos after a later claim; duplicate deliveries are harmless. Without beat, dispatcher credentials or a working broker, queued jobs will not recover automatically; monitor these services. The migration owner must bypass FORCE RLS for the security-definer recovery function. Limit upload bodies at the ingress as well as the gallery-specific ASGI cap.

### Docker Compose

`apps/backend/docker-compose.yml` starts Redis, API, a worker, and one Celery beat scheduler. Set `DATABASE_URL` to the provisioned runtime role and `GALLERY_DISPATCHER_DATABASE_URL` to the separately provisioned dispatcher role in an untracked `apps/backend/.env` or the shell before `docker compose up`. Both database URLs must be reachable from inside containers; for a host database on Docker Desktop, `localhost` inside a container is not the host (use an appropriate host address such as `host.docker.internal`). Apply migrations and provision both roles before starting; keep the migration owner URL out of the running containers. The API receives only `DATABASE_URL`, while the worker receives both URLs and beat receives neither. An empty URL preserves startup of unrelated legacy services but the gallery and its recovery cannot operate until configured. Run exactly one beat instance.

## Tenant administration, provisioning and owner binding

**Deploy order:** apply migration 005, then rerun `python -m app.db.provision_context <runtime-role>`, then deploy the new code. Login calls `claim_tenant_invitations`, so code deployed before the migration and grants makes login fail with 500. The migration role must bypass FORCE RLS (it backfills `events.updated_at` from `created_at`). provision_context is authoritative for `events`, `tenant_branding`, `tenants`, `tenant_domains`, `tenant_memberships` and `tenant_invitations`: it revokes ALL on them from the runtime role (including grants from earlier provisioning or default privileges) and regrants only SELECT (events, branding, tenants, memberships) plus column-level writes (INSERT on id, tenant_id, name, slug, description; UPDATE on name, slug, description, status, updated_at for events; INSERT/UPDATE on palette, colors, logo_png and, for UPDATE, theme_version for branding; `tenant_id`, `logo_url` and `created_at` are not updatable). The runtime role has no DELETE on events and no table privileges on `tenant_invitations`, `tenant_memberships` writes, `tenants` or `tenant_domains` writes.

Tenants are created only by an operator, never over HTTP, with the migration-owner URL (superuser or BYPASSRLS):

```
DATABASE_URL=<migration-owner-url> python -m app.db.provision_tenant --name "Aurora" --slug aurora --hostname aurora.example.com --owner-email owner@example.com
```

It validates name, slug (3-40 chars, reserved names such as admin/api/auth/www rejected), hostname (lowercase DNS name, non-reserved first label) and email, then creates the tenant, hostname and default branding and refreshes a pending owner invitation. Re-running is idempotent; a hostname owned by another tenant is refused. Owner binding: the owner has not logged in, so the invitation stores a normalized email and expires (default 7 days). At login on that tenant's hostname the SECURITY DEFINER function `claim_tenant_invitations` (which raises unless its tenant argument equals the transaction's tenant context) creates the owner membership, or upgrades an existing admin to owner, only if the user's stored email matches. This function is the only membership write the runtime role can cause. `users.email` is stored only when Google reports `email_verified`, so an unverified or spoofed email claims nothing; an invitation is single-use and tenant-scoped. Re-run the command to issue a new invitation. Ownership binds to whoever controls the invited Google account with a verified email, on any domain, so the operator must confirm the address out of band. An existing slug is never assumed to be the same tenant: re-running with the same hostname and owner is idempotent (`created: false`), but a run without the flag only verifies (the hostname is bound and the email is a current owner or has a live, unclaimed, unexpired, unrevoked invitation) and changes nothing. Adding a hostname or a different owner, or reviving an expired, revoked or claimed invitation, requires `--existing-tenant-id <uuid>`, which also revokes (`revoked_at`) other unclaimed invitations; suspended tenants are refused.

Admin API (`app/api/tenant_admin.py`) runs as the runtime role in `tenant_session`, tenant from Host via the session, owner/admin membership required (403 otherwise, 401 anonymous); mutations require same HTTPS Origin and `X-CSRF-Token`. Branding stores a predefined palette key plus resolved colors and a re-encoded PNG logo in `tenant_branding` (bytea under RLS); each change bumps `theme_version`. The public logo URL is `/api/v1/tenant/logo/<token>.png` with an opaque tenant+version token; only the exact current token is served (immutable cache, ETag/304), anything else is 404 `no-store`. Logos are shrunk or quantized to fit 500 kB, else rejected with 422. Legacy routes remain public and unaffected.
